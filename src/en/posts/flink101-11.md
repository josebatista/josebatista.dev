With the local cluster running, it is time to approach Flink from the application side. But I did not want to start by copying ready-made code without knowing where it lives.

The first step was to separate four things:

- **Java project**: code and dependencies
- **Flink Application**: a program that declares a computation
- **Job**: a computation executed by the cluster
- **cluster**: the processes and resources that execute the Job

## The environment

The Flink cluster is already running in Docker. To write the Job, I confirmed Java 21 and Maven:

```bash
java -version
mvn -version
```

The lab follows a simple educational structure:

```text
my-flink-studies/
└── 01-fundamentos/
    └── labs/
        ├── day00/
        │   └── resources/
        │       └── compose.yaml  <- current file
        └── day03/
            ├── pom.xml
            └── src/
                ├── main/
                │   ├── java/dev/josebatista/flink101/day03/
                │   │   └── FirstDataflowJob.java
                │   └── resources/
                └── test/
                    └── java/dev/josebatista/flink101/day03/
```

The code follows the layout Maven recognizes automatically. The directory path corresponds to the `dev.josebatista.flink101.day03` package, while auxiliary files live in `src/main/resources`.

## The minimum dependencies

```xml
<properties>
    <maven.compiler.release>21</maven.compiler.release>
    <flink.version>2.2.1</flink.version>
</properties>

<dependencies>
    <dependency>
        <groupId>org.apache.flink</groupId>
        <artifactId>flink-streaming-java</artifactId>
        <version>${flink.version}</version>
        <scope>provided</scope>
    </dependency>
    <dependency>
        <groupId>org.apache.flink</groupId>
        <artifactId>flink-clients</artifactId>
        <version>${flink.version}</version>
        <scope>provided</scope>
    </dependency>
</dependencies>
```

The `provided` scope exists because the cluster already provides the core libraries. When the application uses additional libraries, they will need to be installed in the cluster or included in the submitted artifact.

## What exists inside the class

A Java application starts in `main`:

```java
package dev.josebatista.flink101.day03;

public class FirstDataflowJob {
    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env =
            StreamExecutionEnvironment.getExecutionEnvironment();

        // The dataflow will be declared here.

        env.execute("day03-first-dataflow");
    }
}
```

This snippet does not describe a useful computation yet. It only locates the elements before the practical work:

- `main` is the Application entry point;
- `StreamExecutionEnvironment` is the context used to declare and configure the Job;
- `execute()` completes the description and requests its execution.

In the next post, I will fill the space between the environment and `execute()`.

## Build and submission

Build and execution are different steps.

Maven generates the JAR:

```bash
mvn -f 01-fundamentos/labs/day03/pom.xml clean package
```

Then, the Flink client in the JobManager submits this JAR:

```bash
docker compose -f 01-fundamentos/labs/day00/resources/compose.yaml exec jobmanager \
  ./bin/flink run /workspace/01-fundamentos/labs/day03/target/flink101-day03-1.0-SNAPSHOT.jar
```
