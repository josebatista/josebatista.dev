In the previous post, I talked about the difference between querying yesterday's logs and following the logs that are still arriving. Now I want to make that more concrete.

## The problem

Imagine we need to receive an alert whenever any service logs more than three errors within five minutes. The incoming stream might look like this:

```text
10:00:11  payment-service  ERROR  card declined
10:01:03  catalog-service  ERROR  product unavailable
10:01:28  payment-service  ERROR  acquirer timeout
10:03:42  payment-service  ERROR  card declined
10:04:17  payment-service  ERROR  acquirer timeout
```

When the last log record arrives, the system should emit something like:

```text
ALERT: payment-service had 4 errors in the last 5 minutes
```

It looks like a simple count. But it isn't.

### What the system needs to remember

When the error at `10:03:42` arrives, it does not carry the information that two other errors have already occurred in `payment-service`. To decide whether to issue an alert, the processor needs to have retained something from that service's previous records.

A simplified version of that memory would look like this:

```text
service: payment-service
observed errors: 10:00:11, 10:01:28, 10:03:42
```

When the record at `10:04:17` arrives, the processor checks that memory, adds the new timestamp, and sees that there are now four errors within the relevant interval.

That memory, which persists from one event to the next, is **state**. It is not just a cache that makes things faster: without it, the processor sees only an isolated event and cannot account for the sequence of events.

### Why separating by service matters

Errors from `catalog-service` cannot be included in the count for `payment-service`. The application therefore keeps an independent context for each key:

```text
payment-service -> [10:00:11, 10:01:28, 10:03:42, 10:04:17]
catalog-service -> [10:01:03]
```

That is what lies behind a seemingly harmless operation such as “group by service.” Each event needs to access the state for the correct group.

### Why five minutes changes everything

If the question were “How many errors has this service had since the application started?”, we could simply keep incrementing a number forever. But an operational alert needs to know what is happening **now**.

At `10:05:12`, the error from `10:00:11` is no longer within the last five minutes. The relevant state needs to stop counting it:

```text
window observed at 10:05:12: 10:00:12 to 10:05:12
```

This slice of time is a **window**. In this example, we want a five-minute sliding window: it does not interrupt the flow of logs; it only defines which events are included in the result at that moment.

State and windows are therefore closely related, but they are not the same thing:

```text
state   -> what the system retains between events
window  -> which events are included in the current calculation
```

## The idea I want to keep

By now, it is clear that the alert is not just a count. The system needs to remember what has already happened and decide which events are still part of the calculation. That is where state and windows come in.

So far, we have assumed that a single machine can handle everything. But what happens when the volume grows and the processing needs to be distributed? That is what I want to explore in the next post.
