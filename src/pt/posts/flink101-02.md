No post anterior, falei da diferença entre consultar os logs de ontem e acompanhar os logs que continuam chegando. Agora quero deixar isso mais concreto.

## O problema

Imagine que a gente precisa receber um alerta quando qualquer serviço registrar mais de três erros em cinco minutos. O fluxo que chega ao sistema pode ser algo assim:

```text
10:00:11  payment-service  ERROR  cartão recusado
10:01:03  catalog-service  ERROR  produto indisponível
10:01:28  payment-service  ERROR  timeout no adquirente
10:03:42  payment-service  ERROR  cartão recusado
10:04:17  payment-service  ERROR  timeout no adquirente
```

No último registro de log, o sistema deve emitir algo como:

```text
ALERTA: payment-service teve 4 erros nos últimos 5 minutos
```

Parece só uma contagem. Mas não é.

### O que o sistema precisa lembrar

Quando o erro das `10:03:42` chega, ele não traz junto a informação de que já aconteceram dois outros erros do `payment-service`. Para decidir se alerta ou não, o processador precisa ter guardado algo dos registros anteriores daquele serviço.

Uma versão simplificada dessa memória seria:

```text
serviço: payment-service
erros observados: 10:00:11, 10:01:28, 10:03:42
```

Quando chega o registro das `10:04:17`, o processador consulta essa memória, inclui o novo horário e percebe que agora há quatro erros no intervalo relevante.

Essa memória que continua existindo de um evento para o outro é o **estado** (*state*). Não é só um cache para deixar tudo mais rápido: sem ela, o processador só enxerga um evento isolado e não consegue calcular a sequência.

### Por que separar por serviço importa

Os erros do `catalog-service` não podem entrar na conta do `payment-service`. Então, a aplicação mantém um contexto independente para cada chave:

```text
payment-service -> [10:00:11, 10:01:28, 10:03:42, 10:04:17]
catalog-service -> [10:01:03]
```

É isso que está por trás de uma operação aparentemente inocente como “agrupar por serviço”. Cada evento precisa encontrar o estado do grupo certo.

### Por que cinco minutos mudam tudo

Se a pergunta fosse “quantos erros esse serviço já teve desde que a aplicação iniciou?”, bastaria aumentar um número para sempre. Mas um alerta operacional quer saber o que está acontecendo **agora**.

Às `10:05:12`, o erro das `10:00:11` já não pertence mais aos últimos cinco minutos. O estado relevante precisa deixar de considerá-lo:

```text
recorte observado às 10:05:12: 10:00:12 até 10:05:12
```

Esse recorte de tempo é uma **janela** (*window*). Neste exemplo, queremos uma janela deslizante de cinco minutos: ela não interrompe o fluxo de logs, só define quais eventos participam do resultado naquele momento.

Por isso, estado e janela são conceitos próximos, mas diferentes:

```text
estado  -> o que o sistema guarda entre eventos
janela  -> quais eventos entram no cálculo atual
```

## A ideia que quero guardar

Agora já dá para perceber que aquele alerta não é só uma contagem. Ele precisa lembrar o que já aconteceu e decidir quais eventos ainda fazem parte da conta. É daí que entram estado e janelas.

Até aqui, estamos imaginando que uma única máquina dá conta de tudo. Mas o que acontece quando o volume cresce e esse processamento precisa ser dividido? É o que quero explorar no próximo post.
